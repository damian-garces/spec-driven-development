# Spec Driven Development (SDD) - Platzi Course

🌐 **Lee esto en otros idiomas:** [Español](./Readme.md)

This repository contains the structure and documentation for the **Spec-Driven Development (SDD)** project from Platzi.

---

## 📌 Project Description

The goal of this repository is to apply the **Spec-Driven Development (SDD)** methodology. This root documents the global environment and required tools, while the actual project is created and implemented in an internal subfolder.

---

## 🛠️ Tools and Requirements

To work on this SDD project, we use the following set of tools and programs.

> **Note about the environment:** This installation was done on **WSL (Windows Subsystem for Linux) on Windows**, using Ubuntu. The documented commands correspond to that environment. If you install directly on Windows, without WSL, the commands and some steps may be different.

### Git

Git manages the code's versions and is required because Spec Kit runs on top of Git.

Installation:

```bash
sudo apt update
sudo apt install -y git
```

Validation:

```bash
git --version
```

### Python

Python is required by Spec Kit to run some internal components.

Installation:

```bash
sudo apt update
sudo apt install -y python3 python3-pip python3-venv python-is-python3
```

Validation:

```bash
python --version
pip --version
```

### uv

`uv` is a tool to manage Python, virtual environments, and packages.

Installation:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
```

If necessary, reload the terminal configuration:

```bash
source "$HOME/.local/bin/env"
```

Validation:

```bash
uv --version
```

### Claude Code

Claude Code is an **AI coding agent** that can be used to work with Spec Kit. Installing it is optional and only necessary if you choose Claude Code as the project's integration.

Installation:

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

Validation:

```bash
claude --version
```

### Spec Kit

Spec Kit is an *open-source* GitHub tool that generates the project's structure and technical specifications.

Installation:

```bash
uv tool install specify-cli --from git+https://github.com/github/spec-kit.git
```

Validation:

```bash
specify --help
```

The installation is considered correct if every validation command shows the version or the corresponding help without errors.

### Choosing the AI coding agent

Spec Kit can work with different AI coding agents. The `--integration` option indicates which one the project will use. Some examples are:

```bash
# Claude Code
specify init spec-driven-project --integration claude

# GitHub Copilot
specify init spec-driven-project --integration copilot

# Codex CLI
specify init spec-driven-project --integration codex
```

You must choose a single option when creating the project and have the corresponding tool installed. To see all the integrations available in your installed version of Spec Kit, run:

```bash
specify integration list
```

### Project initialization

To create the project's subfolder using the Claude Code integration, run:

```bash
specify init spec-driven-project --integration claude
```

In this command, `spec-driven-project` is the name of the folder that will be created for the project. This name was chosen because it clearly describes its purpose. Using `src` is not recommended, since it usually represents only the source-code folder, nor `project`, because it is too generic.

## 🚀 SDD Workflow

1. **Requirements and Initialization:** Set up Git, Python, uv, Claude Code, and Spec Kit.
2. **Specification Generation:** Use Spec Kit inside Claude Code to create the technical contracts and specifications.
3. **Development:** Create the project's subfolder and implement the solution guided by the generated specifications.

### Creating the project constitution

The constitution is the document that defines the project's main rules. It works as a permanent guide for the AI agent and organizes the project from beginning to end through six pillars:

1. **Nature of the project:** defines what the project is, its purpose, and what problem it aims to solve.
2. **Technology stack:** establishes the technologies, tools, and base implementation rules.
3. **Domain rules and hard business logic:** describes the immutable rules the application must respect and the conditions that cannot be broken.
4. **Code structure and style:** defines how the project is organized, how the code is written, and which naming conventions must be followed.
5. **Error handling and validations:** establishes how to validate data and how to communicate errors without exposing technical details to the end user.
6. **Source of truth:** indicates which document has authority over the system's behavior and stops the AI agent when facing contradictions, preventing it from implementing code that isn't backed by the specification.

These six pillars form the anatomy of the constitution and serve as a reference throughout all stages of development.

To generate it, go into the project folder and open Claude Code:

```bash
cd ~/spec-driven-development/spec-driven-project
claude
```

Inside Claude Code, run the slash command `/speckit-constitution` and paste the following content. It's important to include the `/` at the beginning, since that's how Claude Code recognizes the skill as an invocable command:

```markdown
# Project Constitution: Padel Court Booking System

## 1. Nature of the Project
This is an application for booking padel courts. Its purpose is to allow users to authenticate and manage time reservations in specific spaces.

## 2. Technology Stack (Implementation Rules)
- **Frontend / UI:** React. Use Tailwind CSS for styling.
- **Backend:** Node.js with Express.
- **Database:** Local SQLite (file `padel.db`). Do not use heavy ORMs to keep things simple; use `better-sqlite3` or plain SQL statements.
- **Language:** TypeScript across the whole stack.

## 3. Domain Rules and Business Logic
These rules are immutable. The AI agent must strictly respect them:
- **Closed Catalog:** The system ONLY manages 5 fixed courts: Cancha Laureles, Cancha El Poblado, Cancha Belén, Cancha Robledo, and Cancha Envigado.
- **Time Blocks:** Reservations operate on a 24-hour format.
- **Collision Prevention (Double-Booking):** This is the system's critical rule. Under no circumstance can a reservation be written to the database without first validating that the selected court is free at that time.
- **Authentication:** Every booking flow requires an active user session.

## 4. Code Structure and Style
- **Flat Structure:** Avoid over-engineering. Do not implement "Clean Architecture" or complex patterns. Use a simple structure: `/frontend`, `/backend`, and `/db`.
- **Style:** Prioritize functional programming and functional components (Hooks in React). Avoid using classes unless mandatory.
- **Naming:** Use `camelCase` for functions/variables and `PascalCase` for Interfaces/Types.

## 5. Error Handling and Validations
- **UI:** Never expose raw errors or stack traces to the end user. Every technical error must be translated into a friendly message (e.g.: "This court has already been booked at this time").
- **Backend:** Always return semantic HTTP status codes (400 invalid request, 401 not authenticated, 409 booking conflict).

## 6. AI Agent Behavior (SDD Rules)
- **Zero Shadow Code:** Build strictly what is documented in `spec.md`. Do not add "just in case" features (no payment gateways, no complex profiles, etc.).
- **Source of Truth:** If a user instruction contradicts this constitution, or if you detect a logical flaw, stop. Warn about the problem and request an update to `spec.md` before touching the source code.
```

Once finished, Spec Kit will save the constitution in `.specify/memory/constitution.md`. This file must stay inside the repository because it contains the project's shared rules. If the command doesn't appear, close Claude Code and reopen it from `spec-driven-project`, not from the root folder `spec-driven-development`.

### Generating the project specification

The specification describes what the product must do from the users' and the business's perspective. Its goal is to turn a general idea into clear, verifiable, and bounded functional requirements. It also defines the goals of the iteration and what will explicitly not be built, to prevent the AI agent from adding out-of-scope functionality.

Inside Claude Code, run the slash command `/speckit-specify` and paste the following specification:

```markdown
## Main Features

### 1. User Authentication
- Users must be able to register and log in using an email and password.
- Only users with an active session can view full availability and make reservations.
- Users can only manage their own reservations, not those of others.

### 2. Court Exploration and Selection
- The system must statically list the 5 available courts: Cancha Laureles, Cancha El Poblado, Cancha Belén, Cancha Robledo, and Cancha Envigado.
- The user must be able to select a specific date on a calendar to view availability.
- For the selected date, the system must show the 24-hour schedule grid, in 1-hour blocks, for the chosen court.
- The system must clearly indicate which time blocks are "Available" and which are "Booked".
- A user can only have one active reservation at a time.

### 3. Creating Reservations
- The user can select an available time block and confirm their reservation.
- **Critical Rule (Collision Prevention):** Before confirming, the system must re-validate that the block is still available. If another user took the slot in that lapse of time, the reservation must be rejected with a clear error message.
- Reservations can only be made in whole blocks, for example, from 14:00 to 15:00.
- Reservations cannot be made for dates or times that have already passed.

### 4. Managing My Reservations
- The user must have a panel where they can see the list of their upcoming reservations and their history of past reservations.
- Each list item must show: court name, date, and time.
- The user can cancel an upcoming reservation by selecting it in their panel and confirming the action.

## What will NOT be built in this iteration (Non-Goals)

- There will be NO integrated payment gateway; payment will be handled in person at the club.
- There will be NO web admin panel to add, edit, or delete courts; the list of 5 courts is immutable in the code.
- There will be NO external notifications, such as transactional confirmation emails or SMS/WhatsApp messages.
- There will be NO reservations of more than 1 continuous hour in a single click; if someone wants 2 hours, they must make 2 independent reservations.
- There will be NO "matchmaking" system to find playing partners or tournaments.
```

Once finished, Spec Kit will save the specification in the project's artifacts folder. This specification will be the reference for the following steps: planning, task breakdown, and implementation.

### Clarifying the specification

After generating the specification, `/speckit-clarify` is run. This command reviews `spec.md` looking for ambiguous or under-specified areas, asks the user pointed questions to resolve them, and updates the specification with the answers. Its goal is to reduce the risk of incorrect reinterpretation before moving on to technical planning with `/speckit-plan`.

Inside Claude Code, run the slash command `/speckit-clarify` right after creating the `spec` with `/speckit-specify`, and before running `/speckit-plan`.

`/speckit-clarify` can also be run again later, not just the first time. It's used to **correct or refine a requirement that already exists** in `spec.md` (for example, if some data point was poorly defined, such as assuming reservations apply for 24 hours when in reality they should only be allowed during a specific time window of the club). It is not the right command to add a completely new feature that didn't exist in the spec; for that, `spec.md` is updated directly or `/speckit-specify` is run again. If you correct something with `/speckit-clarify` after having generated `plan.md` or `tasks.md`, run `/speckit-plan`, `/speckit-tasks`, and `/speckit-analyze` again so they reflect the change before implementing it.

### Generating the technical plan

Once the specification is clarified, `/speckit-plan` is run. This command takes the already-clarified `spec.md` (the "what") and translates it into a technical plan (the "how"): it defines the architecture, the stack to use, the data models, the contracts between components, and the implementation approach, always respecting the rules already established in the project's constitution.

Inside Claude Code, run the slash command `/speckit-plan` after having run `/speckit-clarify`, since this command depends on the already-clarified specification to build the plan.

The command doesn't deliver a single file, but several artifacts that cover different layers of the project:

- **plan.md:** contains the technical context, the constitution compliance check, and the project structure.
- **research.md:** researches features and the best way to apply them, for example authentication or the single-active-reservation check.
- **Data model:** defines the project's entities, for example what a user is and what a court is.
- **API contract:** establishes how the components communicate with each other.
- **quickstart.md:** indicates how to initialize the backend and the frontend of the application.

Once finished, Spec Kit will save the technical plan in the feature's artifacts folder. This plan will be the base for breaking down the work into concrete tasks with `/speckit-tasks` and then implementing them with `/speckit-implement`.

### Generating tasks

Once the technical plan is created, `/speckit-tasks` is run. This command takes `plan.md` and the rest of the generated artifacts (`research.md`, the data model, the API contract, and `quickstart.md`) and breaks them down into a list of concrete, ordered, actionable tasks, ready to be implemented one by one.

Inside Claude Code, run the slash command `/speckit-tasks` after having run `/speckit-plan`, since this command depends on the already-generated technical plan to build the task list.

Each task in the `tasks.md` file follows the format `[ID] [P?] [Story] Description`, where:

- **ID:** a sequential task identifier, for example `T001`.
- **[P]:** an optional marker indicating that this task can be run in parallel with others, because it touches different files and doesn't depend on pending tasks.
- **[Story]:** indicates which user story the task belongs to (for example `US1`, `US2`, `US3`), so each story can be implemented and tested independently.

Tasks are grouped into phases: **Setup** (initial project structure), **Foundational** (shared infrastructure that blocks all stories), one phase per **user story** (ordered by priority), and optionally **Polish** at the end. Each story phase includes a **Checkpoint**, which describes how to validate that the story already works independently before moving on to the next one.

Once finished, Spec Kit will save the task list in `tasks.md`, inside the feature's artifacts folder. This list will be followed step by step when running `/speckit-implement`.

### Consistency analysis

Before implementing, `/speckit-analyze` is run. This command does a cross-check between `spec.md`, `plan.md`, and `tasks.md`: it detects contradictions between them, specification requirements not covered by any task, tasks not backed by the specification, and possible violations of the project's constitution.

Inside Claude Code, run the slash command `/speckit-analyze` after having run `/speckit-tasks` and before running `/speckit-implement`, to detect and fix inconsistencies before writing any code.

### Implementing the project

Once consistency has been analyzed, `/speckit-implement` is run. This command takes `tasks.md` and executes the tasks in order, respecting the phases (Setup, Foundational, user stories, and Polish), their dependencies, and the tasks marked with `[P]` that can be run in parallel, generating the project's actual code as defined in `plan.md` and validated against `spec.md` and the constitution.

Inside Claude Code, run the slash command `/speckit-implement` as the last step of the flow, after having run `/speckit-analyze`. At the end of each user story, validate its corresponding checkpoint before moving on to the next one.

### Project convergence

`/speckit-converge` evaluates the already-implemented code against `spec.md`, `plan.md`, and `tasks.md`, and adds any detected pending work or deviation as new tasks in `tasks.md`. It's used to close the gap between what was specified and what was actually built, instead of assuming the implementation is complete just because `/speckit-implement` finished running.

Inside Claude Code, run the slash command `/speckit-converge` after `/speckit-implement`. If it detects pending work, run `/speckit-implement` again to complete it, and repeat `/speckit-converge` until it reports that the project has converged.

## 🔄 How to Handle Changes After the Initial Implementation

A project rarely ends after going through the whole flow once. Over time, new requirements, additional features, or bugs appear. The command you start with depends on **how deep** the change is: whether it touches the project's base rules, whether it's a new feature, or whether it's an adjustment to something that already exists.

### 1. New requirement that modifies the project's base rules (affects the constitution)

This happens when the change touches something structural: the technology stack, an immutable business rule, or a code convention (for example, changing the database from SQLite to MySQL).

1. `/speckit-constitution` → updates the affected principle; Spec Kit bumps the document's version.
2. `/speckit-plan` → regenerates the architecture, dependencies, and models according to the new base.
3. `/speckit-tasks` → regenerates the tasks affected by the new stack or rule.
4. `/speckit-analyze` → detects old code or artifacts that no longer comply with the updated constitution.
5. `/speckit-implement` → applies the code changes.
6. `/speckit-converge` → confirms nothing from the previous approach was left unmigrated.

### 2. New requirement that generates a new feature

This happens when something that **didn't exist** in the original scope is added (for example, a notification system), without breaking any rule of the current constitution.

1. `/speckit-specify` → describes the new feature; it can coexist with the existing `spec.md` or create a new one, depending on whether Spec Kit treats it as an independent feature.
2. `/speckit-clarify` → resolves ambiguities in this new specification.
3. `/speckit-plan` → generates the technical plan specific to the new feature.
4. `/speckit-tasks` → generates its tasks.
5. `/speckit-analyze` → validates consistency against the constitution and the rest of the project.
6. `/speckit-implement` → builds the feature.
7. `/speckit-converge` → verifies it was fully implemented.

### 3. Fixing a bug reported by a user that requires modifying the specification

This happens when the current behavior **contradicts** what the specification says, or when the specification described something incorrectly and that's why the system was built wrong (like the 24-hour schedule case in this project).

1. `/speckit-clarify` → fixes the exact point in `spec.md` that was poorly defined.
2. `/speckit-plan` and `/speckit-tasks` → are regenerated **only if** the existing plan or tasks became misaligned with the fix.
3. `/speckit-analyze` → confirms the fix didn't create new inconsistencies.
4. `/speckit-implement` → applies the fix in the code.
5. `/speckit-converge` → validates the bug was fully resolved end to end.

### 4. Fixing a bug that is an implementation error, not a specification error

This happens when the specification was already correct, but the code doesn't comply with it (a programming error). In this case, **the spec is not touched**, because the problem isn't there.

1. Fix the code directly, or ask for the specific fix inside Claude Code without going through `/speckit-specify` or `/speckit-clarify`.
2. `/speckit-analyze` → optional, useful if the fix is large and you want to confirm it's still aligned with `spec.md`, `plan.md`, and `tasks.md`.
3. `/speckit-converge` → optional, to verify no related pending work was left.

In all four cases, the general rule is the same: the change is documented first at the corresponding level (constitution, specification, or none if it's just a code bug), and then Spec Kit is left to propagate that change down to the lower levels, instead of editing the code directly when the real problem lies in the constitution or the specification.
